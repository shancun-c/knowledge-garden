# 开发与发布

本仓库是唯一产品代码主线；不要再创建一份公开目录并手动同步代码。历史备份仅用于查阅和恢复。

## 目录边界

- 仓库内：产品代码、测试、通用文档、无密钥配置模板、第三方许可证。
- 仓库外：真实环境变量、账户与密钥、知识库、图片、导出数据、截图、验收记录和个人部署脚本。
- 本地推荐布局：`knowledge-garden/` 为代码，`private/knowledge-garden/` 为私有资料，`backups/` 为迁移前备份，三者为同级目录。
- 将 `KNOWLEDGE_DATA_DIR` 指向仓库外；推荐绝对路径，避免启动目录改变造成数据目录变化。配置加载方法见 README。
- 不将旧仓库作为远程添加或合并其历史。需要恢复的旧实现按文件审查后移入；旧历史可能包含个人运维信息。
- 历史运维脚本可能含旧路径，不应直接执行；发布前必须核对代码来源、数据路径和目标服务器。

## 开发

1. 从最新 `main` 创建功能分支；先检查工作区，保留其他未提交改动。
2. 修改相关代码，并为有意义的行为变更维护测试。
3. 在仓库根目录运行：

```bash
npm ci
node --experimental-strip-types --test tests/*.test.ts
npx tsc --noEmit
npm run build:selfhost
git diff --check
```

首次克隆在构建前执行类型检查可能缺少 Next.js 生成的类型声明；可以先完成构建，再运行类型检查。不要提交 `next-env.d.ts` 或构建缓存。

4. 查看 `git status` 与暂存差异，确认没有私有资料。按明确文件路径暂存，提交后通过 PR 或经授权的直接推送合入主线。

## 发布

- 以已验证的提交作为发布来源，记录提交号；正式版本使用标签和 GitHub Release。
- 保持版本说明、升级步骤及兼容性说明与实际变更一致。
- 向 GitHub 推送代码不等于部署生产服务器。部署按 `deploy/README.md` 操作，先备份数据与配置，再验证健康、认证、保存与恢复。
- 数据、图片和 AI 设置留在独立持久化目录，不放入发布包。不要为了升级覆盖真实数据。
- 发布前发现远程出现新提交时，先整合并验证，不覆盖他人的历史。
